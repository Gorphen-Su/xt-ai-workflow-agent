# XT Superpowers + OpenSpec 规格驱动开发工作流

## 概述

本 skill 是功能交付的统一入口，结合 OpenSpec（规范与文档管理）和 Superpowers（结构化软件开发方法论）。

核心纪律：**先探索、再锁规范、最后严谨执行**。

所有沟通使用简体中文。

## 关键覆盖（Overrides）

以下规则覆盖任何引用的子工作流中的默认行为：

- **禁用 Git Worktrees**：所有实现工作在当前分支的主工作目录中进行，不使用 worktree。
- **设计文档路径**：`docs/designs/YYYY-MM-DD-<topic>-design.md`
- **实现计划路径**：`docs/plans/YYYY-MM-DD-<topic>.md`
- **OpenSpec 产物路径**：`openspec/changes/<change-name>/`（保持不变）

---

## 阶段 0：需求类型判断

在 Git 状态检查之前，先判断本次需求是主需求还是子需求。

### 判断流程

1. **检查调用参数**：是否包含 `--parent <name>` 参数？
   - **是**：验证 `openspec/changes/<name>/` 是否存在且处于 `in_progress` 状态。
     - 存在 → 本次作为 `<name>` 的子需求。
     - 不存在 → 提示用户父需求不存在，提供可选的主需求列表或建议新建。
   - **否**：进入自动发现流程。

2. **自动发现**（无参时）：
   - 扫描 `openspec/changes/` 目录，查找所有包含 `children.yaml` 的 change（即主需求）。
   - 筛选状态为 `in_progress` 的主需求。
   - **无进行中的主需求** → 自动作为新主需求启动。
   - **有进行中的主需求** → 使用 `ask_user` 询问：
     > 当前有以下进行中的需求：
     > 1. `<change-1>`（3/5 子需求已完成）
     > 2. `<change-2>`（0/2 子需求已完成）
     >
     > 本次需求是：
     > A. 新建一个独立的主需求
     > B. 作为 `<change-1>` 的子需求
     > C. 作为 `<change-2>` 的子需求

3. **确定后**：记录本次需求类型（主/子）和关联的父 change 名称（如有），进入阶段 0B。

---

## 阶段 0B：Git 状态检查（强制前置步骤）

在进入任何工作流阶段之前，必须先执行 Git 状态检查。

### 步骤

1. 运行 `git status --porcelain` 检查是否有未提交的更改。
2. 运行 `git diff --stat` 查看更改概况。
3. **如果仓库是干净的**（无未跟踪文件、无修改）：直接进入阶段 1。
4. **如果仓库有脏状态**：
   a. 向用户展示当前未提交的更改摘要。
   b. 使用 `ask_user` 询问用户："当前仓库有未提交的更改（列出文件）。是否要先提交这些更改再开始新需求？"
   c. **如果用户确认提交**：
      - 运行 `git diff` 查看完整更改内容。
      - 根据更改内容自动生成简洁的中文 commit message。
      - 执行 `git add`（添加具体文件，不使用 `git add -A`）和 `git commit`。
      - 确认提交成功后进入阶段 1。
   d. **如果用户选择不提交**：记录当前状态，在当前脏状态下继续进入阶段 1。
5. 此检查在每次调用本 skill 时都必须执行，不可跳过。

---

## 阶段 1：探索与需求澄清（Explore）

**目标**：理解需求、探索项目上下文、收敛方案。此阶段不写任何生产代码。

### 步骤

1. **阅读项目上下文**：
   - 阅读 `CLAUDE.md` 了解项目规范。
   - 阅读相关已有代码、测试、配置。
   - 理解现有架构和约定。
   - 如果是子需求，阅读父 change 的 `proposal.md`、`design.md`、`specs/` 和 `tasks.md`，理解已有上下文。

2. **澄清需求**：
   - 每次只问一个关键问题。
   - 使用 `ask_user` 获取用户对歧义点的判断。
   - 不要假设，宁可多问一次。

3. **方案比较**：
   - 提出 2-3 个可行方案。
   - 每个方案列出优缺点。
   - 给出推荐方案及理由。
   - 使用 `ask_user` 确认方案选择。

4. **设计文档**：
   - 将确认的方案写入 `docs/designs/YYYY-MM-DD-<topic>-design.md`。
   - 设计文档必须包含：背景、方案选择、技术细节、影响范围。
   - 使用 `ask_user` 确认设计文档后再继续。

### 门禁

- **此阶段不允许编写任何生产代码。**
- **不允许修改 src/ 下的任何源文件。**
- 只允许阅读、分析、编写设计文档。

---

## 阶段 2：规范锁定（Lock Specs）

**目标**：将确认的设计正式化为 OpenSpec 变更产物。此阶段仍然不写生产代码。

### 步骤

1. **确认 change 名称**：
   - 主需求：推导或确认一个 kebab-case 的 change name。
   - 子需求：使用 `<parent-name>--<child-name>` 双横线格式。

2. **创建 OpenSpec change 目录**：`openspec/changes/<change-name>/`

3. **按依赖顺序完成产物**：
   a. `proposal.md` — 为什么要改、改什么
   b. `design.md` — 技术方案和权衡
   c. `specs/.../spec.md` — 规范性需求和行为场景
   d. `tasks.md` — 可执行的实现检查清单

4. **状态验证**：确认所有必需的 OpenSpec 产物已完成。

5. **实现计划**：
   - 将实现计划写入 `docs/plans/YYYY-MM-DD-<topic>.md`。
   - 计划必须与 `tasks.md` 中的任务对应。
   - 使用 `ask_user` 确认实现计划。

6. **主子需求索引**：
   - **如果是主需求**：创建 `openspec/changes/<change-name>/children.yaml`，包含空子需求列表。
   - **如果是子需求**：
     - 在子 change 中创建 `parent-ref.md`，记录父 change 名称和影响的 task 编号。
     - 在父 change 的 `children.yaml` 中添加子需求条目（状态 `pending`）。

### 门禁

- **所有必需的 OpenSpec 产物完成前，不能开始编码。**
- **此阶段不允许编写任何生产代码。**
- `proposal.md` 未完成不能写 `design.md`。
- `design.md` 未完成不能写 specs。
- specs 未完成不能写 `tasks.md`。
- `tasks.md` 未完成不能进入阶段 3。

---

## 阶段 3：严谨执行（Execute）

**目标**：按照锁定的规范和计划，以 TDD 方式实现功能。

### 步骤

1. **子需求状态更新**：如果是子需求，将 `children.yaml` 中对应条目状态更新为 `in_progress`。

2. **TDD 循环**（对每个任务重复）：
   a. **红**：先写一个失败的测试，准确描述期望行为。
   b. **绿**：写最少的代码让测试通过。
   c. **重构**：在测试保护下清理代码，保持功能不变。

3. **持续对齐**：
   - 实现过程中如发现规范需要调整，必须回到阶段 2 更新对应产物。
   - 不允许默默偏离规范。

4. **验证**：
   - 运行完整的测试套件。
   - 运行项目特定的 lint/build 命令。
   - 确保所有测试通过、无 lint 错误。

5. **产物对齐检查**：
   - 代码实现与 `tasks.md` 中的任务一一对应。
   - 测试覆盖与 `specs/.../spec.md` 中的行为场景对应。
   - 设计文档中的技术方案已正确实现。

### 门禁

- **新行为必须先写失败测试，不允许跳过。**
- **没有新的验证输出（测试结果、构建结果），不能声称任务完成。**
- **不允许使用 git worktree。所有工作在当前分支进行。**

---

## 阶段 4：归档与自动提交（Archive & Commit）

**目标**：确认所有工作完成，归档 OpenSpec change，自动提交 Git。

### 步骤

1. **最终验证**：
   - 运行一次完整的测试和构建，获取最新输出。
   - 确认所有测试通过。

2. **三方对齐确认**：
   - 代码实现 vs `tasks.md`：每个任务都有对应实现。
   - 测试覆盖 vs `specs/.../spec.md`：每个行为场景都有测试覆盖。
   - 实际实现 vs `docs/designs/` 中的设计：技术方案一致。

3. **主子需求同步**（如果是子需求）：
   - 将子需求的规格变更（ADDED/MODIFIED/REMOVED）合并到父 change 的主规格中。
   - 更新 `parent-ref.md` 中同步状态为 `synced`。
   - 更新父 change 的 `children.yaml` 中子需求状态为 `completed`，更新 `tasks_done`。
   - 计算父需求进度：`sum(子.tasks_done) / sum(子.tasks_total) × 100%`。
   - 如果所有子需求已完成，通知用户父需求可以进入归档流程。

4. **归档 OpenSpec change**：
   - 标记 change 为已完成状态。
   - 如果是主需求且所有子需求已完成，归档整个主 change。

5. **自动 Git 提交**：
   - 将所有变更文件（代码、测试、文档、OpenSpec 产物）整理为提交。
   - `git add` 添加具体文件（不使用 `git add -A`）。
   - 根据变更内容自动生成 commit message，格式为：
     - 子需求：`feat(<parent>): <child-description>`
     - 主需求：`feat: <main-description>`
   - 执行 `git commit`。

### 门禁

- **实现、测试和规范未对齐前，不能归档。**
- **没有最终验证输出，不能声称完成。**
- **子需求规格变更未同步到父规格前，不能归档。**
- **归档和提交是原子操作，必须一起完成。**

---

## 全局守卫（Guardrails）

以下规则在整个工作流中始终生效，不可绕过：

1. **探索阶段不写生产代码** — 阶段 1 和阶段 2 只产出文档和规范。
2. **TDD 强制执行** — 阶段 3 中所有新行为先写失败测试。
3. **OpenSpec 产物完成前不编码** — 阶段 2 的门禁不通过不能进入阶段 3。
4. **没有新验证输出不声称完成** — 每次声称完成必须附带最新命令输出。
5. **实现、测试、规范对齐前不归档** — 阶段 4 必须确认三方对齐。
6. **归档完成后必须自动执行 Git 提交** — 归档和提交是原子操作。
7. **禁用 git worktree** — 所有实现工作在当前分支进行。
8. **中文沟通** — 所有面向用户的信息使用简体中文。

---

## 阶段转换检查清单

每次准备从当前阶段进入下一阶段时，确认以下条件：

```
阶段 0  → 阶段 0B: 需求类型已确定（主/子），父 change 已确认（如有）
阶段 0B → 阶段 1:  Git 状态已处理（干净或用户选择继续）
阶段 1  → 阶段 2:  设计文档已确认，方案已批准
阶段 2  → 阶段 3:  所有 OpenSpec 产物完成，实现计划已确认，children.yaml/parent-ref.md 已创建
阶段 3  → 阶段 4:  所有任务已实现，测试通过，验证输出已获取
阶段 4  完成:      三方对齐确认，子需求同步完成（如有），归档完成，Git 已提交
```

## 触发条件

在以下情况下使用本 skill：

- 用户明确要求使用 `xt-superpowers-openspec-workflow`
- 用户要求"规格驱动开发"
- 用户要求先设计再编码，且需求非平凡
- 功能需求需要从探索到归档的完整流程
- 用户要求使用 OpenSpec + Superpowers 工作流

## 调用示例

```text
# 新建主需求（无参模式，自动判断）
/xt-superpowers-openspec-workflow 开发用户认证模块

# 指定为子需求（传参模式）
/xt-superpowers-openspec-workflow --parent user-auth-module 登录功能
```
