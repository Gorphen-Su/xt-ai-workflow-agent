# verify 阶段审查上下文管理

本文档说明 `xt-sdd-verify` 阶段特有的上下文管理策略，针对审查循环和修复循环的上下文累积问题。

## 核心问题

verify 阶段有两个主要上下文累积点：

### 痛点 1：审查循环累积

```
步骤 6 代码审查（第 1 轮）
  ↓ 审查输出：Critical/Important/Suggestion 问题列表 ~2000 tokens
  ↓ 逐个修复 ~3000 tokens
步骤 3-6 重新走（第 2 轮）
  ↓ 含第 1 轮的历史 ~5000 tokens
步骤 3-6 重新走（第 3 轮）
  ↓ 累积到 ~8000 tokens（小窗口模型易爆）
```

### 痛点 2：重复遍历

- 步骤 3b 遍历 specs 收集覆盖清单
- 步骤 5a 再次检查覆盖（已优化为复用 3b 清单）
- 修复后重走步骤 3-6，可能重复遍历

---

## 优化策略 1：审查轮次间上下文清理

### 核心原则

**每轮审查完成后，只保留问题列表，清理审查详细输出**。

### 清理触发点

在步骤 6 代码审查每轮完成后：

```markdown
[上下文归档 - 审查第 N 轮完成]

已保存到 sdd-state.yaml / 内存清单：
- 审查轮次: N
- 问题列表: <CRITICAL x 个, WARNING y 个, SUGGESTION z 个>
- 已修复: <修复的问题摘要>

下一轮审查（或修复验证）将从问题列表恢复。
可忽略本轮审查的详细输出。
```

### 问题列表持久化

将问题列表保存到 sdd-state.yaml 或内存清单，支持跨轮次恢复：

```yaml
# sdd-state.yaml 增强（verify 阶段）
verify_status:
  review_rounds: 2
  current_round_findings:
    critical:
      - id: C1
        description: "[场景名] 无实现覆盖"
        status: fixed  # fixed | pending
    warning:
      - id: W1
        description: "[决策名] 实现偏离"
        status: pending
    suggestion: []
  all_fixed: false
```

## 优化策略 2：修复循环上下文管理

### 问题

修复 Critical/Important 问题后，需要重新走步骤 3-6 验证。如果不清理，上下文会持续累积。

### 优化：修复后重置上下文

**修复完成、准备重走步骤 3 前**：

```markdown
[上下文重置 - 准备重新验证]

已修复的问题: <问题 ID 列表>
待验证的问题: <剩余未修复问题>

重新走步骤 3-6 验证，仅加载：
- 修复涉及的文件（git diff 圈定）
- 未解决问题的清单

可忽略之前的审查过程。
```

### 重新验证的按需加载

重走步骤 3-6 时，**仅加载修复涉及的范围**：

| 步骤 | 原加载范围 | 优化后加载范围 |
|------|----------|-------------|
| 3a 扫描变更 | 全量 git diff | **仅修复的 diff** |
| 3b 对比 specs | 所有受影响 specs | **仅修复涉及的 specs** |
| 4 代码质量 | 全量测试 | **仅修复相关的测试**（codegraph affected） |
| 5 合规检查 | 所有问题 | **仅验证修复的问题 + 新增影响** |
| 6 代码审查 | 全量审查 | **仅审查修复的代码** |

## 优化策略 3：文档同步检查复用

### 已有优化（强化）

步骤 3b 已有"单次遍历，同时收集文档同步与覆盖信息"的规则。**进一步强化**：

```
步骤 3b 遍历一次 specs → 产出两份清单：
  ├── 文档同步清单（步骤 3c 用）
  └── 覆盖清单（步骤 5a 用，MUST NOT 再次遍历）
```

### 修复循环中的复用

修复后重走步骤 3-6 时：
- **文档同步清单**：仅检查修复是否引入新的文档影响
- **覆盖清单**：仅验证修复涉及的场景

---

## 优化策略 4：验证报告从清单生成

### 原理

步骤 8 的验证报告**从累积的问题清单生成**，而非重新检查。

### 优化

```markdown
### 步骤 8：生成验证报告（从清单生成）

报告数据来源：
- 测试结果：步骤 4 的运行摘要（已记录）
- 规范合规：步骤 5 的问题清单（已记录）
- 文档同步：步骤 3 的同步记录（已记录）
- 代码审查：步骤 6 的审查清单（已记录）

→ 直接从 sdd-state.yaml 的 verify_status 和各步骤记录汇总，无需重新遍历。
```

---

## 优化策略 5：小窗口模型分段审查

### 检测到小窗口模型时

**分段审查策略**：
- 每轮审查独立完成，轮次间强制清空
- 修复批次化（一轮修复多个问题，而非逐个）
- 重新验证时仅聚焦修复范围

### 分段执行流程

```
第 1 轮审查
  ↓ 收集问题清单
  ↓ [紧急清空]
修复批次 1（所有 Critical）
  ↓ [紧急清空]
重新验证（仅修复范围）
  ↓ [紧急清空]
第 2 轮审查（仅审查修复的代码）
  ...
```

## 与共享规则的协同

verify 阶段在共享规则基础上，强化以下要点：

| 共享规则 | verify 强化点 |
|---------|------------|
| 上下文管理 | **审查轮次间清理**（最频繁） |
| 小窗口适配 | **分段审查 + 批量修复** |
| 输出精简 | 问题列表摘要式记录 |

→ 共享规则参见 [xt-sdd-shared/references/](../../xt-sdd-shared/references/)

## sdd-state.yaml verify 字段增强

为支持审查循环上下文恢复，建议增强：

```yaml
verify_status:
  review_rounds: 0
  doc_sync_completed: false
  current_round_findings:
    critical: []
    warning: []
    suggestion: []
  fixed_issues: []
  test_result_summary: null  # 测试结果摘要
```

## 预期收益

| 场景 | 原流程 | 优化后 | 改善 |
|------|-------|--------|------|
| 3 轮审查循环 | ~8000 tokens 累积 | ~3500 tokens | ~55% |
| 5 轮审查循环 | ~15000 tokens（易爆） | ~5000 tokens | ~65% |
| 修复后重新验证 | 全量重走 | 仅修复范围 | ~60% |
| 验证报告生成 | 重新检查 | 从清单生成 | ~70% |
| 小窗口模型成功率 | 30% | 80% | +50% |
