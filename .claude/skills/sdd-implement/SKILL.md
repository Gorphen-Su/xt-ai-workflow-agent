# SDD 实现阶段

SDD 规格驱动开发的第三阶段：基于规范产物逐任务执行 TDD 循环。

## 铁律

1. **新行为 MUST 先写失败测试，MUST NOT 在未写失败测试的情况下编写实现代码**
2. **每个任务完成后 MUST 要求用户确认，MUST NOT 自动跳过**
3. **发现规范偏离时 MUST 暂停，MUST NOT 默默偏离规范**

## 执行步骤

### 步骤 1：确定当前变更

1. 扫描 `openspec/changes/` 目录，查找进行中的变更
2. 如果只有一个 → 自动选择
3. 如果有多个 → 使用 AskUserQuestion 让用户选择
4. 如果没有 → 提示用户先运行 `/sdd:explore` 和 `/sdd:plan`

### 步骤 2：进度恢复

1. 读取变更目录下的 task-status.md
2. 解析阶段进度：如果 implement 阶段未开始，从头开始
3. 解析任务明细：找到第一个状态为"未开始"或"执行中"的任务
4. 如果所有任务已完成 → 提示用户运行 `/sdd:verify`

### 步骤 3：加载规范上下文

在开始实现之前，MUST 读取变更目录下的所有规范文件：
1. `proposal.md`：了解需求范围和排除范围
2. `design.md`：了解技术方案和架构决策
3. `specs/` 下的所有 spec.md：了解行为场景
4. `tasks.md`：了解任务清单

### 步骤 4：逐任务执行 TDD 循环

对每个未完成的任务，执行以下 TDD 循环：

#### 4a. RED — 编写失败测试

1. 根据 specs 中的场景编写一个准确描述期望行为的失败测试
2. 运行测试确认它失败
3. 将 task-status.md 中该任务状态更新为"执行中"

#### 4b. GREEN — 最小实现

1. 编写最少的代码让测试通过
2. MUST NOT 过度实现（不实现 specs 中未要求的功能）
3. 运行测试确认它通过

#### 4c. REFACTOR — 重构

1. 在测试保护下清理代码，保持功能不变
2. 运行测试确认重构未破坏功能
3. 将 task-status.md 中该任务状态更新为"测试中"

#### 4d. 测试验证

1. 运行完整的测试套件（不仅限于当前任务的测试）
2. 如果全部通过 → 将任务状态更新为"已完成"，记录测试结果
3. 如果有失败 → 将任务状态更新为"已失败"，记录失败原因

### 步骤 5：单任务完成确认

每个任务完成后，使用 AskUserQuestion 展示任务产出摘要，提供三个选项：
- **A. 通过，继续下一个任务**：进入下一个未开始的任务
- **B. 不通过，需要修改**：回到当前任务的 TDD 循环，根据用户反馈修改
- **C. 暂停，稍后继续**：保存当前进度到 task-status.md，退出

### 步骤 6：规范偏离处理

如果实现过程中发现规范需要调整：

1. **暂停当前实现**
2. 向用户说明偏离原因
3. 使用 AskUserQuestion 询问处理方式：
   - **回到 sdd:plan 修改规范**：暂停实现，修改 design.md/specs/tasks.md，修改完成后重新实现受影响的任务
   - **继续实现，记录偏离**：在 task-status.md 中记录偏离说明，后续在 verify 阶段处理
4. MUST NOT 在用户未确认的情况下默默偏离规范

### 步骤 7：所有任务完成

1. 更新 task-status.md 头部阶段进度：implement:✓
2. 展示实现摘要：完成的任务数、失败的测试数（如有）
3. 提示用户运行 `/sdd:verify`

## task-status.md 更新规则

每次状态变更时，更新 task-status.md 中的对应行：

| 时机 | 更新内容 |
|------|---------|
| 开始执行任务 | 状态→执行中，更新时间 |
| 进入测试阶段 | 状态→测试中，更新时间 |
| 测试通过 | 状态→已完成，更新时间，记录测试结果 |
| 测试失败 | 状态→已失败，更新时间，记录失败原因 |

## 常见问题

- "AI 没读规范就实现了"：检查步骤 3 是否执行
- "测试和实现顺序反了"：检查 TDD 循环步骤
- "任务粒度太粗"：在 plan 阶段的 bridge 转换应已拆分；如仍过粗，可在此阶段进一步拆分
- "规范偏离但用户不知道"：步骤 6 的规范偏离处理确保不会默默偏离
