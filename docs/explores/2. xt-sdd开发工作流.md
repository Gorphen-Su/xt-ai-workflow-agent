# xt-sdd规格驱动开发工作流

sdd规格驱动开发工作流。当需要进行功能开发时触发：结合 OpenSpec 规范管理和 Superpowers 软件开发方法论，强制执行"先探索、再锁规范、最后严谨执行"的三阶段流程。Git 状态管理、TDD 强制、验证门禁。当用户要求规格驱动开发、需要先设计再编码、或使用本 skill 名称时触发


## 背景
目前团队在是推动sdd规格驱动开发过程，已经使用上了Openspec 作为规格文档管理的工具，以及superpowers作为代码生成以及执行tdd测试流程等工具，但在使用过程中，由于两个工具之间存在一定的相同性，但是又产生差异，所以我想重新定义一个开发的工作流程。避免直接使用两者的工具，目的是让整体的规格文档达到统一性，方便迭代管理。

## 修改
1. hyperSpec的名称修改为 xt-sdd
2. 根据不同的节点搭配不同的命令例如： /xt-sdd:propose, /xt-sdd:plan ,/xt-sdd:apply, /xt-sdd:archive
3. 将propose 阶段拆分出两个阶段 propose 跟 plan
    3.1 propose 对应 `openspec-propose` 通过 CLI 创建变更目录 + 生成所有 artifacts（proposal、design、specs、tasks）
    3.2 plan 对应 `superpowers:writing-plans` 读取 openspec artifacts，生成 superpowers 格式实现计划
4. 将其apply 阶段对应 拆分 `apply` 跟 `verify`两个阶段
    4.1 apply `superpowers:subagent-driven-development` 或 inline | 按计划执行实现，TDD + 子代理审查 
    4.2 verify `superpowers:verification-before-completion` 全量验证 跟 `superpowers:requesting-code-review`  全局代码审查
5. .hyperspec-state.yaml 修改名为 sdd-state.yaml 放在所属change 对应需求下面，方便做到独立需求任务同时迭代管理，那关于属于项目级的信息，例如项目架构等信息，则应该是在openspec.yaml中增加部分信息作为项目级信息存储，方便每个阶段读取使用。
6. 每个阶段完成后提示用户是否调到下个阶段继续
7. 最后归档完成之后提示用户是否需要提交git, 并把所有相关的代码以及文档依赖等整理成清单作为日志提交，另外在归档之前，确认所有计划checkbox 是否已勾选，按照hyperspec的规则进行。
8. 此功能为增加当前项目级的skill 以及命令实现，不能依赖旧的已经实现过的skill 以及命令, 但是openspec 以及 superpowers工具中的skill 以及命令除外。
