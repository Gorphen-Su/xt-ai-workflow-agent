# HyperSpec vs SDD 对比分析

## 1. 架构总览对比

| 维度 | HyperSpec | SDD |
|------|-----------|-----|
| 阶段数 | 3（propose → apply → archive） | 5（explore → plan → implement → verify → archive） |
| 定位 | 纯编排层，委托原生 skill 执行 | 自包含 skill，每个阶段有完整执行逻辑 |
| 核心依赖 | Superpowers skill + OpenSpec CLI | OpenSpec CLI（无 Superpowers 依赖） |
| 状态文件 | `.hyperspec-state.yaml`（项目根目录） | `sdd-state.yaml`（随变更目录存放） |
| 项目 profile | 内嵌于状态文件 | 独立文件 `sdd-project-profile.yaml` |
| 规范产出 | 委托 openspec-propose + writing-plans | 自行生成 design.md / specs/ / tasks.md |
| 实现方式 | 委托 superpowers:subagent-driven-development | 自行执行 TDD 循环 |
| 验证方式 | 委托 verification-before-completion + requesting-code-review | 自行双重验证（代码质量 + 规范合规） |

### 阶段映射

```
HyperSpec                          SDD
─────────                          ───
propose ──────────────────────→ explore + plan
  ├─ 项目分析                      ├─ 项目分析器（explore 步骤 2）
  ├─ 需求确认                      ├─ 需求澄清（explore 步骤 5）
  ├─ 调用 openspec-propose         ├─ 产出 proposal.md（explore 步骤 6）
  └─ 调用 writing-plans            ├─ 生成 design.md（plan 步骤 3a）
                                   ├─ 生成 specs/（plan 步骤 3b）
                                   └─ 生成 tasks.md + bridge 转换（plan 步骤 3c-4）

apply ────────────────────────→ implement + verify
  ├─ 智能执行模式选择               ├─ TDD 循环逐任务执行（implement 步骤 4）
  ├─ 全模式：subagent 并行          ├─ 编译检查 + 测试验证（implement 步骤 4d）
  ├─ 轻量模式：内联执行             ├─ 规范偏离处理（implement 步骤 6）
  ├─ 代码审查循环（≤3 次）          ├─ 代码质量验证（verify 步骤 3）
  └─ 验证                          └─ 规范合规检查（verify 步骤 4）

archive ──────────────────────→ archive
  ├─ 规范一致性验证                 ├─ 归档前验证（archive 步骤 2）
  ├─ 调用 openspec-archive-change   ├─ 生成 archive.md（archive 步骤 3）
  └─ 分支处理 + 清理状态文件        └─ 同步 specs + 归档（archive 步骤 4-5）
```

## 2. 已采纳的 HyperSpec 特性

### 2.1 项目分析器（Project Profiler）

**HyperSpec 实现**：SKILL.md 中定义 Project Profiler，自动检测语言、框架、构建工具、编译/测试命令、项目结构、CI 配置。支持 Maven/Gradle/npm/Go/Cargo/Python 六种构建工具。含构建命令映射表和运行时验证。

**SDD 采纳**：sdd-explore 步骤 2，在 HyperSpec 基础上增加：

| 增强项 | 说明 |
|--------|------|
| 编译约束自动提取 | 根据技术栈提取 compile_constraints（编译型语言约束接口+实现同 Task 等） |
| 空白项目（greenfield）处理 | 无源码时跳过自动探测，在需求确认中一并确认技术栈 |
| 独立 profile 文件 | 输出到 `openspec/sdd-project-profile.yaml`，与 `openspec.yaml` 分离，避免污染 OpenSpec 配置 |
| 环境问题立即阻塞 | 编译命令运行时验证失败且为环境问题（JDK/Node 版本不匹配等）时立即阻塞等用户确认 |

### 2.2 结构化状态管理

**HyperSpec 实现**：使用 `.hyperspec-state.yaml` 跟踪进度，含 version、active_change、phase、checkpoint、project_profile 字段。状态文件是缓存，实际文件是真实来源。含断点恢复映射表。

**SDD 采纳**：`sdd-state.yaml`，在 HyperSpec 基础上增加：

| 增强项 | 说明 |
|--------|------|
| 任务级 checkpoint | 每个任务有独立 checkpoint（null → red → green → refactor → complete），粒度更细 |
| 阶段级 checkpoint 映射 | `phase_checkpoints` 记录每个阶段的进度，支持跨阶段恢复 |
| cascade 字段 | 级联回退意图记录（last_affected_phase、invalidated_from、reason、preserved_tasks） |
| review_counters | 区分任务级重试计数（task_retries）和全局审查轮次（global_review_rounds） |
| 状态文件随变更存放 | 放在 `openspec/changes/<name>/sdd-state.yaml`，归档时随迁保留作历史记录 |
| 一致性验证 | checkpoint 声称任务完成但实际代码未体现时，回退到上一确认一致的状态 |

**状态文件结构对比**：

```yaml
# HyperSpec: .hyperspec-state.yaml
version: 1
active_change: <name>
phase: propose | apply | close
checkpoint: <字符串>
project_profile: { ... }

# SDD: openspec/changes/<name>/sdd-state.yaml
version: 1
change: <name>
phase: explore | plan | implement | verify | archive
checkpoint: <字符串>
phase_checkpoints:
  explore: <checkpoint> | null
  plan: <checkpoint> | null
  implement: <checkpoint> | null
  verify: <checkpoint> | null
  archive: <checkpoint> | null
tasks:
  - id: 1
    description: <描述>
    status: pending | in_progress | completed | failed
    updated: <时间>
    test_result: <结果>
    checkpoint: null | red | green | refactor | complete
review_counters:
  global_review_rounds: 0
  task_retries: {}
cascade:
  last_affected_phase: null
  invalidated_from: null
  reason: null
  preserved_tasks: []
```

### 2.3 审查循环限制

**HyperSpec 实现**：apply 阶段代码审查最多 3 轮，超过后建议回到 propose 阶段。

**SDD 采纳**：调整为 5 次，并区分两级：

| 层级 | SDD 实现 | 计数器 |
|------|---------|--------|
| 任务级 | sdd-implement 单任务修改不超过 5 次 | `review_counters.task_retries[任务id]` |
| 全局级 | sdd-verify 审查循环不超过 5 轮 | `review_counters.global_review_rounds` |

**调整原因**：SDD 的 TDD 循环粒度更细（RED → GREEN → REFACTOR → 验证），单任务可能需要多次微调才能通过完整测试套件，5 次比 3 次更合理。

## 3. 采纳后的改进与差异

### 3.1 级联回退归一

SDD 将级联执行逻辑归一到 sdd-plan，这是 HyperSpec 没有的概念。

**HyperSpec 做法**：apply 阶段审查超限 → 建议回到 propose。无级联规则，无重置范围选择。

**SDD 做法**：

- sdd-implement / sdd-verify 发现需要回退 → 只在 `cascade` 字段写入回退意图
- sdd-plan 启动时检测到 `cascade.invalidated_from != null` → 执行级联重置
- 级联规则矩阵：

| 被修改的阶段 | 影响范围 | 说明 |
|-------------|---------|------|
| explore | plan + implement + verify 全部失效 | 范围变更影响所有后续 |
| plan | implement + verify 失效 | 设计变更影响实现和验证 |
| implement | 仅 verify 失效 | 实现变更只需重新验证 |
| verify | 无级联 | 仅 verify 内部重做 |

- 重置范围选择：全量重置（默认）或选择性保留已完成任务
- 归一化好处：避免 implement/verify 中重复执行级联逻辑导致不一致

### 3.2 状态文件位置差异

| 方案 | 优点 | 缺点 |
|------|------|------|
| HyperSpec：根目录全局唯一 | 简单，一个文件管所有变更 | 无法同时跟踪多个变更，归档后状态丢失 |
| SDD：随变更目录存放 | 天然支持多变更并行，归档时随迁保留 | 每个变更一个状态文件 |

### 3.3 项目 profile 独立文件

HyperSpec 将 project_profile 内嵌于状态文件。SDD 拆分为独立的 `openspec/sdd-project-profile.yaml`：

- 避免污染 `openspec.yaml`（OpenSpec CLI 配置）
- 避免嵌入状态文件（项目信息不随变更而变，属于全局信息）
- 所有变更共享同一份 profile

## 4. 未采纳的 HyperSpec 特性及原因

| HyperSpec 特性 | 描述 | 未采纳原因 |
|---------------|------|-----------|
| 智能执行模式 | 根据任务数、跨模块性选择 full（subagent 并行）或 lightweight（内联） | SDD 不依赖 Superpowers 的 subagent 机制，采用串行逐任务执行 |
| Git worktree 支持 | apply 阶段可选在 worktree 中工作 | SDD 明确禁用 worktree，串行推进，避免分支管理复杂度 |
| 委托原生 skill 执行 | propose 调用 openspec-propose，apply 调用 subagent-driven-development | SDD 是自包含 skill，不依赖外部 skill 执行具体逻辑 |
| 环境预检（apply 阶段） | 开始实现前验证编译环境可用 | SDD 在 explore 阶段就做运行时验证，提前阻塞环境问题 |
| 代码审查循环 | 调用 requesting-code-review skill，3 轮 | SDD 用 verify 阶段的双重验证（代码质量 + 规范合规）替代 |
| 自动 commit | 一任务一提交，每完成一个任务自动 git commit | SDD 交给用户决定提交时机，不自动提交 |
| 用户意图覆写 | 用户明确指定阶段时直接执行 | SDD 通过 sdd-state.yaml 的 checkpoint 自动路由，用户意图通过选择不同 /sdd:xxx 命令表达 |

## 5. SDD 独有特性（HyperSpec 无对应）

| 特性 | 描述 | 价值 |
|------|------|------|
| TDD 强制循环 | RED（写失败测试）→ GREEN（最小实现）→ REFACTOR（重构），铁律级别 | 确保每个行为都有测试覆盖，防止过度实现 |
| Bridge 转换 | specs 场景 → TDD 测试用例映射，design 决策 → 实现任务映射，粗任务 → TDD 步骤拆分 | 规范到实现的自动桥接，减少人为遗漏 |
| 双重验证 | 代码质量（测试套件）+ 规范合规（场景覆盖、决策遵循、排除范围、主规范兼容） | 确保实现既正确又合规，代码质量 ≠ 规范合规 |
| 级联回退机制 | 规则矩阵 + 全量/选择性重置 + cascade 字段 + 归一化执行 | 受控回退而非简单重做，避免级联污染 |
| 编译约束注入 | 从 project profile 提取 compile_constraints，注入任务拆分逻辑（编译独立性原则） | 确保每个任务完成后可独立编译通过 |
| 向后兼容迁移 | 检测旧格式 task-status.md → 自动迁移到 sdd-state.yaml | 平滑过渡，不破坏已有工作流 |
| Bridge compile_constraints 注入 | 任务拆分时遵循"编译独立性"，接口+实现同 Task | 防止拆分出无法独立编译的任务 |
| 规范偏离暂停 | 实现中发现规范需要调整时暂停，必须用户确认 | 防止默默偏离规范 |

## 6. 总结

HyperSpec 和 SDD 代表了两种不同的设计哲学：

- **HyperSpec**：轻量编排，委托原生 skill，自适应执行模式，3 阶段快速闭环
- **SDD**：重度纪律，TDD 强制，双重验证，5 阶段严谨闭环

SDD 从 HyperSpec 采纳了 3 项高价值特性（项目分析器、结构化状态管理、审查循环限制），并根据自身 TDD 纪律和规范合规要求做了适配增强。SDD 独有的 Bridge 转换、双重验证、级联回退机制是其核心差异化能力，HyperSpec 目前没有对应实现。
