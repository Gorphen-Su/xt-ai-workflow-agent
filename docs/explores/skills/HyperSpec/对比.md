# HyperSpec vs SDD 工作流对比分析

## 一、架构对比总览

| 维度 | HyperSpec | SDD |
|------|-----------|-----|
| **阶段划分** | 3 阶段：propose → apply → archive | 5 阶段：explore → plan → implement → verify → archive |
| **核心理念** | 纯编排层，委托原生 skill | 统一封装，内联核心逻辑 |
| **状态管理** | `.hyperspec-state.yaml`（结构化 YAML + checkpoint） | `task-status.md`（Markdown 表格） |
| **委托方式** | 显式调用 `openspec-propose`、`superpowers:writing-plans` 等原生 skill | 内联 OpenSpec CLI 命令 + Bridge 转换 + TDD 逻辑 |
| **项目感知** | 自动探测语言/框架/构建工具，生成 project_profile | 无，依赖 OpenSpec CLI 已有机制 |
| **执行模式** | 智能选择：完整模式（子代理）/ 轻量模式（内联） | 统一内联执行 |
| **断点恢复** | checkpoint 序列 + 实际文件双重验证，7+ 种恢复场景 | 基于 task-status.md 进度标记恢复 |
| **计划文件** | `superpowers/plans/YYYY-MM-DD-<name>.md`（带 checkbox） | 无独立计划文件，任务直接在 tasks.md + task-status.md 中管理 |
| **Commit 纪律** | 每个 task 完成自动 commit，编译前置 | 无自动 commit 机制 |
| **自主模式** | 支持（跳过交互式确认） | 不支持，每阶段强制用户确认 |

### 阶段映射

HyperSpec 的 3 阶段与 SDD 的 5 阶段存在对应关系：

| HyperSpec | SDD | 说明 |
|-----------|-----|------|
| propose Step 1-2 | sdd-explore | 项目分析 + 需求澄清 |
| propose Step 3 | sdd-plan Step 3 | 生成 OpenSpec 规范产物 |
| propose Step 4 | sdd-plan Step 4（Bridge 转换） | 生成实现计划 / TDD 步骤拆分 |
| apply Step 1 | sdd-implement | 逐任务执行 |
| apply Step 2 | sdd-verify Step 3 | 测试验证 |
| apply Step 3 | sdd-verify Step 4 | 代码审查 / 规范合规 |
| archive Step 1 | sdd-verify Step 4（部分） | 一致性验证 |
| archive Step 3 | sdd-archive | 归档 |

关键差异：SDD 将验证独立为单独阶段（verify），且拆分出双重验证（代码质量 + 规范合规）；HyperSpec 将验证和审查嵌入 apply 阶段。

## 二、HyperSpec 特色功能清单

以下逐项列出 HyperSpec 有而 SDD 缺失的机制，含说明、对比和采纳建议。

### 1. 项目分析器（Project Profiler）

**HyperSpec 做法**：首次运行时自动扫描项目，探测语言、框架、构建工具、编译/测试命令、项目结构（monorepo/single-module）、CI 配置。生成 `project_profile` 写入状态文件，后续阶段自适应使用。

**SDD 现状**：完全没有项目感知。sdd-verify 中"识别项目的测试命令"是临时的（检查 package.json、Makefile 等），sdd-implement 中无编译检查，每个阶段都缺少技术栈上下文。

**采纳价值：极高**。项目感知是所有后续自适应行为的基础——编译命令、测试命令、项目结构等信息在多个阶段都需要，且目前 SDD 每次都临时推导或不推导。

**采纳建议**：
- 在 `sdd-explore` 中增加项目分析步骤，产出 `project_profile` 保存到 task-status.md 头部或独立文件
- sdd-implement 使用 `compile_command` 在每个 task 完成后做编译检查
- sdd-verify 使用 `test_command` 替代临时推导
- 空白项目（greenfield）特殊处理：在需求确认中一并确定技术栈

### 2. 结构化状态管理 + 断点恢复

**HyperSpec 做法**：使用 `.hyperspec-state.yaml` 存储 `phase` + `checkpoint` + `active_change` + `project_profile`。定义了完整的 checkpoint 序列（propose 5 个、apply 6 个、archive 4 个），每个 checkpoint 有明确的触发时机。断点恢复基于"状态文件 vs 实际文件"双重验证，15+ 种恢复场景覆盖了各种中断情况。核心原则：**实际文件是 ground truth，状态文件只是缓存**。

**SDD 现状**：使用 `task-status.md`（Markdown 表格）跟踪阶段进度和任务状态。恢复机制较简单：读取 task-status.md，找第一个"未开始"或"执行中"的任务继续。没有 checkpoint 概念，无法精确定位中断位置。

**采纳价值：高**。跨会话开发是常见场景，当前 SDD 的恢复粒度太粗——只能恢复到任务级别，无法恢复到任务内的具体步骤（如"正在写测试"还是"正在写实现"）。

**采纳建议**：
- 在 task-status.md 中增加 checkpoint 字段，记录当前阶段的精确进度
- 为每个阶段定义断点恢复表（不需要像 HyperSpec 那样复杂，3-5 个关键 checkpoint 即可）
- 保留 Markdown 格式（比 YAML 更易读易编辑），但增加结构化字段
- 不需要独立的状态文件——SDD 禁用了 worktree，单需求串行推进，task-status.md 足够

### 3. 框架 API 验证上下文

**HyperSpec 做法**：在 propose 阶段调用 writing-plans 之前，扫描项目中与本次变更同层的已有代码，提取关键框架 API 的实际签名（关注重载、import 路径、构建命令可用性），整理为"框架 API 注意事项"附加到计划生成上下文中。

**SDD 现状**：sdd-plan 的 Bridge 转换不包含 API 验证。生成的 tasks.md 和 TDD 步骤可能引用错误的 API 签名，导致 implement 阶段反复试错。

**采纳价值：高**。这是减少实现阶段"编译失败→修复→再编译"循环的有效手段。AI 生成代码时最常见的问题就是使用了错误的方法重载或过时的 import 路径。

**采纳建议**：
- 在 `sdd-plan` 的 Bridge 转换步骤中增加"API 上下文验证"子步骤
- 扫描变更涉及模块的已有代码，提取实际 API 签名
- 将验证结果注入到 tasks.md 的 TDD 步骤中，作为额外约束
- 实施难度低，不需要改变 SDD 的整体架构

### 4. 智能执行模式选择

**HyperSpec 做法**：根据任务数量、任务独立性、跨模块性、项目结构、变更复杂度等多因子分析，自动选择完整模式（subagent-driven-development，子代理并行执行）或轻量模式（当前会话内联执行）。还有"独立性否决"规则——即使任务多，如果编译依赖强也优先轻量模式。

**SDD 现状**：统一内联执行，没有模式选择。

**采纳价值：中**。当前 SDD 禁用了 worktree 且串行推进，子代理并行模式暂时不适用。但多因子分析的思路可以用于判断是否需要更细致的 TDD 步骤拆分。

**采纳建议**：
- 短期：暂不采纳子代理并行模式（与 SDD 串行推进原则冲突）
- 长期：如果未来放开 worktree 限制，可引入模式选择逻辑
- 可参考的思路：根据任务复杂度调整 TDD 步骤粒度——简单任务用轻量 TDD，复杂任务用完整 RED-GREEN-REFACTOR

### 5. Checkbox 唯一性约束

**HyperSpec 做法**：要求计划文件中每个 Step 的 checkbox 描述全局唯一，推荐格式 `- [ ] **Step N: <动作描述>（Task <编号>）**`。目的是确保 apply 阶段用 Edit 工具更新 checkbox 时 `old_string` 精确匹配，不会误改其他步骤。

**SDD 现状**：tasks.md 使用 `- [ ] X.Y 任务描述` 格式，但 SDD 实际上不使用 Edit 工具来更新 tasks.md 的 checkbox——它更新的是 task-status.md 的表格。所以这个问题在 SDD 中不存在于 tasks.md，但存在于 task-status.md 的更新操作中。

**采纳价值：中**。SDD 使用 task-status.md 的表格行来跟踪状态，用 Edit 工具更新时同样存在 `old_string` 匹配精度问题。

**采纳建议**：
- 在 task-status.md 的任务明细表中增加唯一标识列（如 `#` 编号列已有），确保 Edit 更新时 old_string 包含编号+任务描述，足以唯一匹配
- 当前格式 `| 1 | <任务1描述> | 未开始 |` 已经足够唯一，此项为低优先级改进

### 6. 计划质量审查

**HyperSpec 做法**：writing-plans 生成计划后，必须执行计划质量审查，检查编译约束遵守、import 语句正确性、无效代码、类型一致性。发现问题直接在计划文件中修复。此步骤不可跳过，即使自主模式也必须执行。

**SDD 现状**：sdd-plan 生成 tasks.md 后没有质量审查步骤。Bridge 转换是自动执行的，没有后续验证。

**采纳价值：高**。AI 生成的任务分解和 TDD 步骤可能存在逻辑问题（如跨任务编译依赖、import 路径错误），审查能显著减少实现阶段的问题。

**采纳建议**：
- 在 `sdd-plan` 的 Bridge 转换后增加"任务分解质量审查"子步骤
- 审查维度：
  - 任务间编译依赖（是否需要跨任务同时修改接口和实现）
  - TDD 步骤完整性（每个任务是否都有 RED-GREEN-REFACTOR）
  - API 签名正确性（与项目实际代码对照）
  - 排除范围遵守（任务是否超出 proposal 的 What Changes 范围）
- 发现问题直接修复 tasks.md，不进入 implement

### 7. 编译约束注入

**HyperSpec 做法**：在调用 writing-plans 时，将编译约束作为上下文传入，例如"接口层和实现层分开定义在不同的 Task 中会导致单独编译失败，必须在同一 Task 中同时修改接口和实现"。计划质量审查中也会检查此约束是否被遵守。

**SDD 现状**：没有编译约束概念。Bridge 转换不考虑编译依赖，可能导致拆分的任务无法独立编译通过。

**采纳价值：高**（对编译型语言项目），**低**（对解释型语言项目）。本项目是 Node.js/TypeScript 项目，编译约束相对宽松，但随着项目复杂度增加，这个问题会变得重要。

**采纳建议**：
- 在 `sdd-plan` Bridge 转换中注入编译约束上下文
- 如果 project_profile 的 compile_command 非 null，标记本项目需要编译检查
- 在任务拆分时遵循"编译独立性"原则：一个任务完成后必须能编译通过
- 此项与"项目分析器"联动——需要先知道 compile_command 才能判断编译约束

### 8. 审查循环限制

**HyperSpec 做法**：全局审查循环上限为 3 次，超过则提示用户可能需要回到 propose 阶段重新审视设计方案。同一 task 的修改也限 3 次。

**SDD 现状**：没有明确的审查循环限制。sdd-implement 的"单任务完成确认"和"规范偏离处理"理论上可以无限循环。

**采纳价值：中**。防止 AI 与用户陷入无限修改循环是实用的防护机制。

**采纳建议**：
- 在 `sdd-implement` 中增加任务级修改上限（建议 3 次）
- 超过上限时提示用户：可能需要回到 `sdd:plan` 重新审视任务拆分
- 在 `sdd-verify` 的 CRITICAL 问题修复中同样设置上限

### 9. 降级方案

**HyperSpec 做法**：当原生 skill 不可用时（Skill 工具返回 "Unknown skill"），提供 CLI 回退路径：
- `openspec-propose` 不可用 → 手动 `npx @fission-ai/openspec` 命令
- `openspec-archive-change` 不可用 → 手动 `mv` 归档操作

**SDD 现状**：没有显式的降级方案。但 SDD 的设计本身就是"内联核心逻辑 + CLI 命令"的方式，不太依赖外部 skill 的可用性。

**采纳价值：低**。SDD 的架构已经避免了 HyperSpec 那样的 skill 委托依赖问题——OpenSpec CLI 是主要依赖，如果 CLI 不可用，降级到手动操作的意义有限。

**采纳建议**：
- 可以在 SDD skill 中增加 OpenSpec CLI 不可用时的提示信息
- 不需要完整的降级执行路径

### 10. 自主模式支持

**HyperSpec 做法**：如果用户声明自主执行意图（"完全自主""你决定""不用确认"），跳过交互式需求确认，直接根据需求描述进入下一步。但关键 checkpoint（如 plan-generated）仍必须原子性写入，即使用户声明自主模式。

**SDD 现状**：每阶段强制用户确认（三选项：通过/不通过/暂停），没有自主模式。

**采纳价值：中**。对于信任 AI 判断的用户，强制确认会降低效率。但 SDD 的"先探索、再锁规范、最后严谨执行"理念本身就强调人工把关。

**采纳建议**：
- 在 `sdd-explore` 中增加自主模式选项：如果用户明确说"自主执行"，可跳过逐步确认
- 保留关键节点的确认（如 proposal.md 产出后、所有规范产物完成后）
- 自主模式下 checkpoint 仍必须写入（采纳 HyperSpec 的"原子性 checkpoint"理念）

### 11. Commit 纪律

**HyperSpec 做法**：每个 task/fix 完成后自动 commit，格式 `<类型>(<范围>): <task描述>`。提交流程：编译检查 → 更新 checkbox → 更新状态文件 → commit。全程不做 push。

**SDD 现状**：没有自动 commit 机制。sdd-explore 中有 Git 状态前置检查（脏工作区可选提交），但 implement 阶段没有每个 task 后的自动 commit。

**采纳价值：高**。原子性提交是工程纪律的核心——每个 task 对应一个 commit，让代码历史可追溯、可回滚。当前 SDD 可能在 implement 阶段累积大量变更后一次性提交，增加回滚成本。

**采纳建议**：
- 在 `sdd-implement` 的每个任务 TDD 循环完成后增加自动 commit 步骤
- commit 前运行编译检查（需要 project_profile 的 compile_command）
- commit message 格式：`<类型>(<模块>): <任务描述>`
- 更新 task-status.md 后一起 commit
- 全程不做 push

### 12. 用户意图覆盖

**HyperSpec 做法**：用户可以显式指定阶段（"先做规格""直接开始实现""归档收尾"），跳过状态检测直接进入指定阶段。但如果前置条件不满足（如没有计划文件却要求实现），仍会提醒用户。

**SDD 现状**：不支持阶段跳转。用户必须按 explore → plan → implement → verify → archive 顺序执行。

**采纳价值：低**。SDD 的严格顺序是设计决策，防止跳过关键阶段。但允许在满足前置条件时跳转是合理的。

**采纳建议**：
- 短期：不采纳，保持严格顺序
- 长期：可考虑在前置条件满足时允许跳转，如已有 proposal.md 可直接进入 plan

## 三、SDD 优势保留

以下列出 SDD 已有但 HyperSpec 没有的特色，说明为何保留。

### 1. 五阶段细粒度划分

SDD 的 5 阶段比 HyperSpec 的 3 阶段更细粒度，特别是：
- **explore 独立为第一阶段**：强调"先探索"的纪律性，HyperSpec 将探索压缩为 propose 的子步骤
- **verify 独立为第四阶段**：强调"双重验证"（代码质量 + 规范合规），HyperSpec 将验证嵌入 apply

**保留理由**：细粒度阶段让每个阶段的"铁律"更清晰，用户更容易理解和遵守。SDD 的"先探索、再锁规范、最后严谨执行"理念通过 5 阶段更好地体现。

### 2. 规范合规检查（spec-compliance-check）

SDD 的 sdd-verify 内置了 4 个维度的规范合规检查：
- 场景实现覆盖检查
- 架构决策遵循检查
- 排除范围违反检查
- 主规范兼容检查

HyperSpec 的 archive 阶段只有"规格一致性验证"（检查 design/specs/tasks 是否在代码中体现），没有这么细致的合规维度。

**保留理由**：规范合规检查是 SDD 的核心价值——确保实现不仅"能跑"，还"符合规范"。4 个维度的检查比 HyperSpec 的单一维度更全面。

### 3. Bridge 转换机制

SDD 的 sdd-plan 内置 Bridge 转换，自动将 OpenSpec 产物（specs 场景）映射为 TDD 测试用例。这确保了"规范→测试"的可追溯性。

HyperSpec 依赖 `superpowers:writing-plans` 来做类似的事情，但 writing-plans 生成的是 Superpowers 格式的计划，不是 OpenSpec 格式的 tasks.md——两种产物格式不同，需要额外的同步逻辑。

**保留理由**：Bridge 转换让 SDD 的产物体系保持自洽——从 specs 到 tasks 到测试用例，全部在 OpenSpec 框架内。不需要引入 Superpowers 的计划格式作为中间产物。

### 4. task-status.md 的可读性

SDD 使用 Markdown 表格（task-status.md）跟踪状态，虽然不如 YAML 结构化，但对用户来说更可读、可编辑。用户可以直接打开文件查看进度，也可以手动修改状态。

HyperSpec 的 `.hyperspec-state.yaml` 是机器优化的，用户不太会直接阅读。

**保留理由**：SDD 面向用户（不是面向机器），可读性优先。但可以在 Markdown 中增加结构化字段来弥补精确度不足。

### 5. 每阶段强制用户确认

SDD 的每个阶段完成都必须用户确认（三选项：通过/不通过/暂停），这是"铁律"级别的约束。

HyperSpec 的 propose 阶段有用户确认，但 apply 阶段更偏自动化（子代理执行），archive 阶段依赖 `openspec-archive-change` 内部的确认。

**保留理由**：SDD 强调人工把关，每个阶段转换都需要用户确认，防止 AI 自作主张。这与"先探索、再锁规范、最后严谨执行"的理念一致。

### 6. 归档双源信息合并

SDD 的 archive.md 合并了 OpenSpec（proposal/design/specs）和 Superpowers（task-status 执行记录）两个来源的信息，形成完整的变更记录。

HyperSpec 的归档主要依赖 `openspec-archive-change`，没有生成独立的归档文档。

**保留理由**：archive.md 是变更的可追溯记录，合并双源信息让归档不仅仅是"移动目录"，而是"知识沉淀"。

## 四、采纳优先级排序

按"实施难度 × 价值"排序，推荐以下采纳顺序：

### 第一优先级：高价值 + 低难度

| # | 功能 | 实施难度 | 价值 | 涉及 SDD 阶段 | 说明 |
|---|------|---------|------|--------------|------|
| 1 | 项目分析器 | 低 | 极高 | sdd-explore | 新增步骤，不影响现有逻辑 |
| 2 | 审查循环限制 | 低 | 中 | sdd-implement, sdd-verify | 增加计数器和提示，改动极小 |
| 3 | Checkbox / 行唯一性 | 低 | 中 | sdd-implement | 当前格式已基本满足，仅需文档化约束 |

### 第二优先级：高价值 + 中难度

| # | 功能 | 实施难度 | 价值 | 涉及 SDD 阶段 | 说明 |

## 五、总结

HyperSpec 和 SDD 的核心差异在于**架构哲学**：

- **HyperSpec** 是"纯编排层"——自己不做任何业务逻辑，只负责状态检测、阶段路由、委托原生 skill。优势是解耦和复用，代价是依赖多个外部 skill 的可用性。
- **SDD** 是"统一封装"——将 OpenSpec 和 Superpowers 的核心能力内联到 5 个 skill 中。优势是自洽和简洁，代价是 skill 内部逻辑较重。

HyperSpec 最值得 SDD 采纳的不是架构层面的改变，而是**工程细节层面的增强**：项目分析器让后续阶段有了技术栈感知，编译约束和 API 验证减少实现阶段的试错，审查循环限制防止无限循环，Commit 纪律让代码历史可追溯。这些增强都不需要改变 SDD 的架构，只需要在现有阶段中增加步骤和规则。

SDD 应保留的核心优势是：五阶段细粒度划分、规范合规检查、Bridge 转换机制、每阶段强制确认。这些是 SDD 的"灵魂"，不应该为了简化而牺牲。
